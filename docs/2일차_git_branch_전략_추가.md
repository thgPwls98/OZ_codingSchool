## 1. 브랜치 전략이란?

여러 개발자가 하나의 Git 저장소에서 협업할 때 **브랜치를 어떻게 생성하고, 작업하고, 병합할지 정해 놓은 규칙과 작업 흐름(Workflow)** 을 브랜치 전략이라고 한다.

각 개발자가 독립된 브랜치에서 작업하면 다른 사람의 코드를 직접 수정하지 않고도 여러 기능을 동시에 개발할 수 있다.

프로젝트 규모, 개발 인원, 배포 주기 등에 따라 적절한 전략을 선택하는 것이 중요하다.

### 🍳 비유: 브랜치 = 나만의 조리대

하나의 주방(Repository)에서 여러 요리사가 같은 냄비에 동시에 재료를 넣으면 요리가 엉망이 될 수 있다.

따라서 각자 자신의 조리대(Branch)에서 요리한 다음, 완성된 요리를 검토하고 하나의 완성 접시(main)에 합치는 방식이다.

### 브랜치 전략이 필요한 이유

| 이점 | 설명 |
|---|---|
| 독립적인 동시 작업 | 각 개발자가 다른 브랜치에서 작업하므로 작업 내용을 분리할 수 있다. |
| 작업 추적 | 브랜치를 기능이나 이슈 단위로 나누어 변경 목적과 이력을 확인할 수 있다. |
| 작업 단위 롤백 | 문제가 발생하면 관련 커밋을 찾아 변경 사항을 되돌리기 쉽다. |
| 배포 버전 관리 | Git 태그(tag)를 활용하여 특정 출시 버전을 기록하고 관리할 수 있다. |
| 협업 효율성 | PR과 코드 리뷰를 통해 변경 사항을 확인한 후 병합할 수 있다. |

대표적인 브랜치 전략에는 **Git Flow**와 **GitHub Flow**가 있다.

### 자주 사용하는 Git 용어

| 용어 | 의미 | 비유 |
|---|---|---|
| Repository | 프로젝트 저장소 | 팀 공유 폴더 |
| Branch | 독립적인 개발 흐름 | 나만의 작업 공간 |
| Commit | 변경 사항을 기록하는 단위 | 게임 세이브 포인트 |
| Push | 로컬 커밋을 원격 저장소에 전송 | 작업 내용 업로드 |
| Pull | 원격 변경 사항을 가져와 현재 브랜치에 반영 | 최신 공동 작업 내용 반영 |
| PR (Pull Request) | 브랜치 병합을 요청하는 기능 | 보고서 결재 요청 |
| Review | 변경된 코드 검토 | 결재 전 검토 |
| Merge | 서로 다른 브랜치의 변경 이력 통합 | 작업 결과 합치기 |
| Rebase | 커밋을 다른 기준 커밋 위에 다시 적용 | 최신 원본 위에 작업 다시 쌓기 |
| Conflict | Git이 변경 내용을 자동으로 통합하지 못하는 상황 | 같은 문장을 서로 다르게 수정한 상황 |

## 2. Git 기본 명령어

### 브랜치란?

브랜치는 Git에서 특정 커밋을 가리키는 포인터이며, 개발 과정에서는 독립적인 작업 흐름을 만드는 데 사용한다.

새로운 기능을 개발할 때 별도의 브랜치를 생성하면 `main` 브랜치에 직접 영향을 주지 않고 작업할 수 있다.

### 주요 명령어

```bash
# 로컬 브랜치 목록 확인
git branch

# 원격 브랜치까지 확인
git branch -a

# 브랜치 생성
git branch feature/login

# 브랜치 이동
git switch feature/login

# 브랜치 생성과 이동을 동시에
git switch -c feature/login

# main 브랜치로 이동
git switch main

# 병합이 완료된 브랜치 삭제
git branch -d feature/login

# 브랜치 강제 삭제 (주의)
git branch -D feature/login
```

**주의:** `git branch -D`는 병합되지 않은 작업이 있어도 브랜치를 삭제할 수 있으므로 신중하게 사용해야 한다.

## 3. Git Flow

Vincent Driessen이 2010년에 제안한 브랜치 모델이다.

**개발, 기능 추가, 출시 준비, 긴급 버그 수정 등을 역할별 브랜치로 분리하여 체계적으로 버전을 관리하는 방식**이다.

정기적인 출시 일정이 있거나 여러 버전을 관리해야 하는 프로젝트에서 활용할 수 있다.

### 브랜치 종류

| 브랜치 | 역할 | 생성 및 병합 방향 |
|---|---|---|
| `main` (`master`) | 출시된 제품의 안정적인 코드 관리 | 출시 버전 반영 |
| `develop` | 다음 출시를 위한 개발 코드 통합 | `main`에서 생성 |
| `feature/*` | 새로운 기능 개발 | `develop` → `develop` |
| `release/*` | 출시 전 테스트 및 버그 수정 | `develop` → `main`, `develop` |
| `hotfix/*` | 출시 후 긴급 버그 수정 | `main` → `main`, `develop` |

### 🍽️ 비유: 큰 레스토랑 주방

- `main` = 손님에게 제공된 완성 요리
- `develop` = 주방에서 개발 중인 메뉴
- `feature` = 요리사 각자의 조리대
- `release` = 손님에게 제공하기 전 최종 점검
- `hotfix` = 이미 제공된 요리에 문제가 생겨 긴급 수정

여러 단계를 거쳐 검증하기 때문에 관리 과정은 복잡하지만, 출시 전 점검 절차를 체계적으로 운영할 수 있다.

### 개발 흐름

```text
feature ──→ develop ──→ release ──→ main
               ↑            │         │
               └────────────┘         │
               ↑                      │
               └──── hotfix ←─────────┘
```

1. **기능 개발:** `develop`을 기준으로 `feature/login`과 같은 기능 브랜치를 생성한다.
2. **개발 코드 통합:** 기능 개발이 끝나면 PR을 생성하고 코드 리뷰를 받은 뒤 `develop`에 병합한다.
3. **배포 준비:** 출시 시점에 `develop`에서 `release` 브랜치를 생성한다.
4. **테스트 및 수정:** `release`에서 최종 테스트를 진행하고 발견된 버그를 수정한다.
5. **배포:** 테스트가 완료되면 `release`를 `main`에 병합하고 버전 태그를 생성한다. 수정 내용은 `develop`에도 반영한다.
6. **긴급 수정:** 배포 후 문제가 발견되면 `main`에서 `hotfix`를 생성하고 수정 후 `main`과 `develop`에 반영한다.

### 실무에서 활용할 수 있는 팁

**① 환경별 테스트**

- `develop`: 개발 환경에서 기능 통합 테스트
- `release`: 배포 직전 환경에서 최종 검증
- `main`: 실제 출시 버전 관리

단, 브랜치와 서버 환경이 반드시 일대일로 대응해야 하는 것은 아니다.

**② 이슈 번호를 이용한 브랜치 관리**

```bash
# GitHub Issue #10에 해당하는 기능 개발
git switch -c feature/10-login
```

```bash
git commit -m "feat: #10 로그인 API 추가"
```

이슈 번호를 연결하면 어떤 작업을 위해 코드를 수정했는지 추적하기 쉽다.

**③ 작업 브랜치 최신화**

```bash
git fetch origin
git rebase origin/develop
```

기준 브랜치의 변경 사항을 작업 브랜치에 반영한다.

단, Rebase는 커밋 이력을 변경하므로 여러 사람이 함께 사용하는 브랜치에서는 주의해야 한다.

### 장점

- 개발 버전과 출시 버전을 명확하게 구분할 수 있다.
- `release`, `hotfix`를 통해 출시와 긴급 수정 절차를 체계적으로 관리할 수 있다.
- 정기 배포나 여러 버전의 유지보수에 적합하다.

### 단점

- 브랜치 종류가 많아 관리가 복잡하다.
- 브랜치 병합 및 동기화 작업이 자주 발생한다.
- 작은 팀이나 짧은 프로젝트에서는 불필요한 관리 비용이 생길 수 있다.
- 빠른 기능 출시가 필요한 프로젝트에서는 절차가 부담스러울 수 있다.

## 4. GitHub Flow

GitHub에서 제안한 단순한 브랜치 전략이다.

**`main` 브랜치와 작업 브랜치를 중심으로 개발하고, PR과 코드 리뷰를 통해 빠르게 병합하는 방식**이다.

Git Flow와 달리 별도의 `develop`, `release`, `hotfix` 브랜치를 필수로 두지 않는다.

### 브랜치 종류

| 브랜치 | 역할 |
|---|---|
| `main` | 항상 배포 가능한 상태를 유지하는 기본 브랜치 |
| `feature/*` | 기능 추가 등 개별 작업을 수행하는 브랜치 |
| `fix/*` | 버그 수정을 위한 작업 브랜치 |
| `docs/*` | 문서 수정 등을 위한 작업 브랜치 |

`feature`, `fix`, `docs`는 브랜치의 목적을 구분하기 위한 이름 규칙이며, GitHub Flow에서 반드시 정해진 명칭은 아니다.

### 🚚 비유: 푸드트럭

요리사가 새로운 메뉴를 개발하면(feature) 사장님이 맛보고(Review), 문제가 없다고 판단하면 바로 판매(main)하는 방식이다.

큰 레스토랑처럼 여러 단계의 검증 절차를 두기보다는 간단한 구조로 빠르게 작업한다.

단, 검토가 부족하면 문제가 있는 코드가 `main`에 반영될 수 있으므로 코드 리뷰와 자동화 테스트가 중요하다.

### 개발 흐름

```text
main       ──●──────────●──────────●────→
               \        / \        /
feature/login   ●──●───   \      /
                            ●──●──
                          fix/error
```

1. `main`에서 작업 브랜치를 생성한다.
2. 새로운 기능을 개발하거나 버그를 수정한다.
3. 변경 사항을 Commit하고 원격 저장소에 Push한다.
4. GitHub에서 `main`을 대상으로 PR을 생성한다.
5. 팀원에게 코드 리뷰를 요청하고 피드백을 반영한다.
6. 테스트와 리뷰가 완료되면 `main`에 Merge한다.
7. 배포 정책에 따라 배포하고, 사용이 끝난 브랜치를 삭제한다.

### 주요 특징

- `main`을 중심으로 단순하게 운영한다.
- 모든 변경 사항은 짧은 작업 브랜치에서 개발한다.
- PR과 코드 리뷰를 통해 협업한다.
- CI/CD를 활용해 테스트와 배포를 자동화하기 좋다.
- 기능을 작은 단위로 자주 병합하는 방식에 적합하다.

### 장점

- 브랜치 구조가 단순해 배우기 쉽다.
- 빠른 개발과 지속적인 배포에 적합하다.
- PR을 중심으로 코드 리뷰 문화를 형성할 수 있다.
- 브랜치 관리 부담이 적다.

### 단점

- 별도의 출시 준비 브랜치가 없어 테스트와 리뷰 절차를 잘 갖춰야 한다.
- 여러 출시 버전을 동시에 유지보수하는 프로젝트에서는 추가 전략이 필요할 수 있다.
- `main`의 안정성을 유지하지 못하면 배포에 영향을 줄 수 있다.

**중요:** GitHub Flow가 Git Flow보다 반드시 불안정한 것은 아니다. 안정성은 브랜치 개수뿐 아니라 테스트 자동화, 코드 리뷰, 배포 정책 등에 따라 달라진다.

## 5. Git Flow vs GitHub Flow

| 구분 | Git Flow | GitHub Flow |
|---|---|---|
| 핵심 구조 | 역할별 브랜치 분리 | `main` 중심의 단순 구조 |
| 주요 브랜치 | main, develop, feature, release, hotfix | main, 작업 브랜치 |
| 복잡도 | 높음 | 낮음 |
| 배포 방식 | 출시 버전 단위로 관리 | 작은 변경 사항을 자주 병합·배포 |
| 테스트 | release 등 단계별 검증 가능 | PR, CI 등을 통한 병합 전 검증 |
| 배포 속도 | 상대적으로 느릴 수 있음 | 빠른 배포에 유리 |
| 버전 관리 | 출시 브랜치를 활용한 관리 | 태그와 추가 브랜치 등으로 관리 가능 |
| 적합한 환경 | 정기 출시, 다중 버전 유지보수 | 지속적 배포, 소규모·대규모 웹 서비스 모두 가능 |
| 관리 부담 | 상대적으로 큼 | 상대적으로 작음 |

### 어떤 전략을 선택해야 할까?

**Git Flow가 적합한 경우**

- 정해진 일정에 맞춰 제품을 출시하는 경우
- 출시 버전과 개발 버전을 명확히 구분해야 하는 경우
- 여러 버전을 동시에 유지보수해야 하는 경우
- 별도의 출시 준비 및 검증 절차가 필요한 경우

**GitHub Flow가 적합한 경우**

- 기능을 빠르게 개발하고 자주 배포하는 경우
- 팀원 간 PR과 코드 리뷰를 중심으로 협업하는 경우
- 브랜치 관리 절차를 단순하게 유지하고 싶은 경우
- 자동화 테스트와 CI/CD를 활용하는 경우

정답은 없으며, **프로젝트의 규모뿐 아니라 배포 주기, 버전 관리 요구사항, 팀의 협업 방식**을 기준으로 선택하는 것이 중요하다.

## 6. Pull Request(PR)와 코드 리뷰

Pull Request는 작업 브랜치의 변경 사항을 다른 브랜치에 병합하도록 요청하는 GitHub 기능이다.

PR을 통해 팀원들이 코드를 검토하고 의견을 나눈 뒤 변경 사항을 반영할 수 있다.

### PR 생성 방법

1. 작업 브랜치를 원격 저장소에 Push한다.
2. GitHub 저장소에서 **Pull requests → New pull request**를 선택한다.
3. `base`(병합 대상)와 `compare`(작업 브랜치)를 설정한다.
4. PR 제목과 변경 사항을 작성한다.
5. Reviewers, Assignees, Labels 등을 지정한다.
6. PR을 생성하고 리뷰를 요청한다.

예시:

```text
base: main
compare: feature/login
```

`Able to merge`가 표시되면 GitHub가 감지한 병합 충돌이 없다는 의미다. 코드의 기능이나 테스트가 정상이라는 뜻은 아니다.

### 코드 리뷰 방법

PR의 **Files changed** 탭에서 수정된 코드를 확인한다.

필요한 부분에 댓글을 작성한 후 리뷰 결과를 제출한다.

| 리뷰 유형 | 의미 |
|---|---|
| Comment | 의견이나 질문을 남김 |
| Approve | 변경 사항을 승인 |
| Request changes | 병합 전 수정이 필요한 사항 요청 |

리뷰 피드백을 반영한 뒤 추가 Commit과 Push를 하면 기존 PR에 변경 내용이 반영된다.

**코드 리뷰는 단순히 잘못된 부분을 지적하는 과정이 아니라, 코드의 품질을 높이고 팀원 간 지식을 공유하는 과정이다.**

### Merge 방식 3가지

| 방식 | 설명 | 특징 |
|---|---|---|
| Create a merge commit | 병합 커밋을 새로 생성 | 브랜치 병합 이력이 명확함 |
| Squash and merge | 작업 브랜치의 커밋을 하나로 합쳐 병합 | main의 커밋 이력이 깔끔함 |
| Rebase and merge | 커밋을 대상 브랜치 위에 재적용 | 선형적인 이력 유지 |

작은 기능 단위로 개발하는 팀에서는 `Squash and merge`를 선택하여 PR 하나를 하나의 커밋으로 관리할 수도 있다.

### main 브랜치 보호하기

GitHub 저장소의 **Settings → Rules → Rulesets**에서 브랜치 보호 규칙을 설정할 수 있다.

대표적인 규칙은 다음과 같다.

- `Require a pull request before merging`: PR을 통한 병합 요구
- `Required approvals`: 지정된 수의 리뷰 승인 요구
- `Require conversation resolution`: 리뷰 대화 해결 요구
- `Require status checks to pass`: 자동화 테스트 등 필수 검사 통과 요구

실제 적용 가능 여부는 저장소 유형과 GitHub 요금제·권한에 따라 달라질 수 있다.

### Issue와 PR 연결하기

GitHub Issue로 작업을 등록하면 각 이슈에 번호가 부여된다.

```text
Issue #5: 로그인 API 구현
Branch: feature/5-login
PR: 로그인 API 구현
```

PR 본문에 다음과 같이 작성하면 병합 시 관련 이슈를 자동으로 닫도록 설정할 수 있다.

```text
Closes #5
```

단, 자동 종료는 GitHub의 기본 브랜치 및 PR 병합 조건에 따라 동작한다.

## 7. 충돌(Conflict) 해결

Git Conflict는 서로 다른 브랜치에서 변경한 내용을 Git이 자동으로 합칠 수 없을 때 발생한다.

대표적으로 같은 파일의 같은 부분을 서로 다르게 수정한 경우 발생하지만, 파일 삭제와 수정이 동시에 이루어지는 경우 등에도 발생할 수 있다.

### 📝 비유: 같은 문장을 다르게 수정한 공유 문서

A 개발자는 다음과 같이 수정했다.

```python
print("안녕하세요")
```

B 개발자는 같은 부분을 다음과 같이 수정했다.

```python
print("반갑습니다")
```

Git은 어떤 변경이 올바른지 판단할 수 없으므로 개발자가 직접 해결해야 한다.

### 충돌이 발생하는 상황

```text
원격 main
A ─── B ─── C
       \
        L1 ─── L2
          내 feature/login
```

`main`의 C 커밋과 작업 브랜치의 L1 또는 L2 커밋이 같은 부분을 다르게 수정했다면 병합이나 Rebase 과정에서 충돌할 수 있다.

### 충돌 표시 읽는 방법

```text
<<<<<<< HEAD
print("hello")
=======
print("hi")
>>>>>>> feature/login
```

- `<<<<<<< HEAD`: 현재 병합 기준의 변경 사항
- `=======`: 두 변경 사항을 구분하는 선
- `>>>>>>> feature/login`: 상대 브랜치의 변경 사항

위 예시는 Merge 상황을 기준으로 한다. Rebase에서는 `HEAD`가 가리키는 쪽이 달라질 수 있으므로 실제 변경 내용을 확인해야 한다.

### 충돌 해결 순서

1. 충돌이 발생한 파일을 연다.
2. 어떤 변경 사항을 남길지 판단한다.
3. 필요한 코드를 수정하고 충돌 표시를 제거한다.
4. 수정한 파일을 스테이징한다.
5. 진행 중이던 작업을 완료한다.

```bash
# 충돌 상태 확인
git status

# 파일 수정 후
git add 수정한파일
```

**Rebase 중이라면**

```bash
git rebase --continue
```

**Merge 중이라면**

```bash
git merge --continue
```

### 충돌 해결을 취소하고 싶다면

```bash
# Rebase 취소
git rebase --abort

# Merge 취소
git merge --abort
```

### 충돌을 줄이는 방법

- 작업 브랜치를 너무 오래 유지하지 않는다.
- 기준 브랜치의 변경 사항을 주기적으로 반영한다.
- 여러 사람이 같은 파일을 수정해야 한다면 미리 소통한다.
- 기능을 작은 단위로 나누어 작업한다.
- 충돌이 발생하면 관련 코드를 작성한 팀원과 함께 해결한다.

**핵심 정리**

Git Flow는 **역할별 브랜치를 통해 출시 버전을 체계적으로 관리하는 전략**이고, GitHub Flow는 **main과 작업 브랜치를 중심으로 PR·리뷰·병합을 빠르게 반복하는 전략**이다.

어떤 전략이 무조건 좋은 것은 아니며, 팀의 규모와 프로젝트 특성에 맞게 선택하고 일관된 협업 규칙을 지키는 것이 중요하다.

최현영: md 초안 작성, ③ 회원 추가 (feature/create-user)
강선영: md 초안 작성, ④ 회원 수정 (feature/update-user)
서민서: (휴가)
김지영: md 초안 작성, ② 특정 회원 조회 + ⑤ 회원 삭제 (feature/get-delete-user)
