# 혜진 담당: 진료기록 수정·삭제 구현

현재 브랜치는 ⑩ PATCH 및 ⑪ DELETE를 구현한다. 다른 담당자의 공통 기반은 대신 구현하지 않는다. 공통 기반 없이도 단위 테스트를 실행할 수 있지만 실제 DB·파일 연동 완료를 의미하지 않는다.

## 구현 파일

경로는 `AH_web_development_assignment/app/` 기준이다.

- `apis/medical_record_apis.py`: multipart 입력, 의료진 권한, PATCH·DELETE 라우터. `main.py`에 등록했다.
- `schemas/medical_record.py`: 수정 입력 검증과 공통 응답 초안. 선영님의 스키마와 병합 시 통합한다.
- `repositories/medical_record_repository.py`: 기록 잠금, 차트 번호 중복 조회, 이미지·히트맵 경로 수집, 교체 시 기존 이미지·AI 행 삭제, 응답 조회. commit하지 않는다.
- `services/medical_record_service.py`: 환자→기록 잠금, 수정·삭제 트랜잭션, 커밋 전 실패 시 새 파일 정리, 커밋 후 기존 파일 정리.

## 공통 기반 연결

공통 기반 모듈이 없으면 해당 API는 인증·권한 확인 후 503으로 응답한다. 기존 API는 계속 로드된다.

전달받은 확정 규격에 맞춰 `FileCleanupService(db)` 인스턴스를 주입한다. `enqueue`는 동기 함수이며, 파일 저장·삭제와 `run`·`resume`·잠금은 비동기로 호출한다.

| 모듈 | 사용하는 함수 |
|---|---|
| `core/file_storage.py` | `save_xray_image(upload, patient_id) -> str`, `delete_xray_file(image_url)` |
| `repositories/patient_repository.py` | `PatientRepository(db).lock(patient_id)` |
| `services/file_cleanup_service.py` | `FileCleanupService(db).enqueue(target_type, target_id, files)`, `await run(jobs)`, `await resume(target_type, target_id)` |

파일 경로는 `[(file_kind, 상대 경로), ...]`로 수집한다. 저장소는 X-Ray를 `xray`, 히트맵을 `heatmap`으로 구분하므로 동일한 상대 경로도 종류별 저장 루트에서 삭제한다. 라우터 연결부는 공통 `TARGET_MEDICAL_RECORD`와 `cleanup_incomplete_error`를 사용한다. 새 파일 롤백 정리에는 `FILE_KIND_XRAY`를 사용한다.

- `enqueue`는 같은 세션에 작업을 추가하고 commit하지 않는다. 호출에 `await`를 붙이지 않는다.
- 서비스가 데이터 변경과 작업을 함께 commit한다.
- `await run(jobs)`는 완료 상태를 별도 트랜잭션으로 저장한다. `False`이면 `cleanup_incomplete_error()`를 발생시킨다. 예외도 같은 정리 미완료 500으로 변환한다. 이미 커밋한 이미지 교체를 되돌리거나 새 파일을 삭제하지 않는다.
- DELETE는 자원 조회 전에 `await resume(TARGET_MEDICAL_RECORD, record_id)`를 호출한다. `None`이면 일반 삭제·404 판단으로 진행하고, `False`이면 500이다. `True`이면 기록 존재 여부를 확인해 이미 삭제된 기록은 204로 처리하고, 기록이 남아 있으면 정상 삭제를 이어간다.
- 실패한 새 파일 정리는 원래 트랜잭션 rollback 후 별도 정리 작업으로 commit한다. DB 자체가 계속 실패하면 영속화할 수 없으므로 복구 한계가 남는다.
- 환자·기록·이미지·AI CASCADE 및 `passive_deletes`는 지영님 기반 마이그레이션이 필요하다. 현재 모델 상태에서는 실제 DELETE 완료를 보장하지 않는다.
- 임시 의료진 의존성은 현재 권한 정책을 구현했다. 선영님의 `MedicalStaffUser` 병합 후 공통 의존성으로 통합한다.
- DB 세션의 UTC 정책과 기존 시간 데이터 확인은 공통 기반에서 처리한다. 현재 응답은 datetime을 그대로 직렬화하며 `Z` 응답 정책은 공통 스키마 병합 시 통합해야 한다.
- 이 브랜치는 수정·삭제 구현 범위가 확정됐다는 전제로 작성했다. 프론트엔드 수정·삭제 화면은 포함하지 않는다.

## 검증

프로젝트 의존성과 `tests/requirements.txt`가 설치된 환경에서:

```sh
cd AH_web_development_assignment
python -m unittest discover -s tests -p 'test_medical_record_changes.py'
```

권한·입력 검증, 증상만 수정 시 이미지·AI 보존, 이미지 교체 순서, DB 실패 시 새 파일 정리, 정리 실패의 영속화, 커밋 후 정리 실패, DELETE 재요청의 `None`·`True`·`False` 분기와 동기 `enqueue` 호출을 검증한다. 파일 종류별 경로 수집은 SQLite 쿼리로 확인한다. 기반 병합 후 실제 MySQL의 CASCADE·UNIQUE·동시 요청 잠금, 실제 이미지 저장·히트맵 정리·재처리 실행 경로, UTC 응답을 통합 검증한다.
