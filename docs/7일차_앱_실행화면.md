## 1. 개요

| 항목 | 내용 |
|---|---|
| 목표 | 정적 프론트엔드 템플릿(`static/`)과 백엔드 API를 연결하고, 실제 브라우저에서 엔드포인트별 동작을 확인 |

## 3. 화면별 상세

### 1) 홈 · 로그인 화면 (비로그인 상태)

- `/`에서는 서비스 소개와 **로그인하여 시작하기** 버튼이 표시됩니다.
- 로그인하지 않은 상태로 **보호 페이지에 접근하면 로그인 화면으로 이동**합니다(15번 참고).
- 로그인 폼에는 **비밀번호 보기** 버튼과 **회원가입** 링크가 있습니다.

![로그인 화면](images/day7/01_home.png)

### 2) 회원가입 · `POST /api/v1/users/signup`

- 이메일, 이름, 부서, 성별, 전화번호, 비밀번호를 JSON으로 보냅니다.
- 성공(201)하면 **"회원가입이 완료되었습니다. 로그인해주세요."** 알림 뒤 로그인 화면으로 이동합니다.
- 새 계정의 권한은 기본값 `pending`(승인 대기)입니다.

![회원가입 완료](images/day7/02_signup.png)

### 3) 로그인 (승인 대기 계정) · `POST /api/v1/users/login`

- 로그인은 `FormData`(username, password)로 보내고, 응답 본문의 액세스 토큰을 저장합니다.
- 권한이 `pending`이면 다른 메뉴로 가지 못하고 **"관리자의 승인을 기다리는 중입니다."** 안내만 보입니다.

![승인 대기 홈](images/day7/03_login_pending.png)

### 4) 회원 관리 (관리자 전용)

**`GET /api/v1/admin/users?query=&department=`**

- 관리자 메뉴의 회원 관리에서 전체 회원 4명이 조회됩니다.
- 관리자 본인(김의사)의 권한 선택칸은 **비활성화**되어 스스로 권한을 바꿀 수 없습니다.

![회원 목록](images/day7/04_admin_users.png)

- 이름·이메일 검색: `박` 입력 → 박대기 1명

![이름 검색](images/day7/04_admin_search.png)

- 부서 필터: `연구진` 선택 → 최현영 1명

![부서 필터](images/day7/04_admin_filter.png)

**`PATCH /api/v1/admin/users/role`**

### 12) AI 폐렴 예측

**`POST /api/v1/medical-records/{id}/predict`**

- **AI 예측 결과보기** 버튼을 누르면 EfficientNet-B0 5-Fold 앙상블 모델이 X-Ray를 판독합니다.
- 첫 요청은 결과를 새로 저장하고 **201**을 반환합니다. 결과: **Negative, 신뢰도 83.28%, `efficientnet_b0-5fold`**

![AI 예측 결과](images/day7/12_predict_result.png)

- 같은 버튼을 한 번 더 눌러도 모델을 다시 돌리지 않고 **기존 결과를 200으로 재사용**합니다. 수행 일시(오후 3:58:24)와 결과 행 수가 그대로인 것으로 확인했습니다.

![기존 결과 재사용](images/day7/12_predict_reuse.png)

**`GET /api/v1/medical-records/{id}/analyses`** · 수행 일시, 폐렴 여부, 신뢰도, 사용 모델을 표로 표시하고, 양성은 빨간색, 음성은 초록색으로 구분합니다.

| 상황 | 상태코드 | 프론트 동작 |
|---|---|---|
| 첫 예측 | 201 | 성공 알림 후 결과 표 새로고침 |
| 이미 결과 있음 | 200 | 성공 알림, 같은 결과 유지 |
| 모델 미로딩 | 503 | "AI 예측 실패: 잠시후 다시 시도해주세요." 알림 (5-B 참고) |
| 이미지 손상 | 422 | "AI 예측 실패: " + 백엔드 오류 문구 |
| 예측 중 이미지 교체 | 409 | "AI 예측 실패: " + 백엔드 오류 문구 |

#### 12-1) 정상 X-Ray인데 Positive로 판정 (위양성)

> 캡처·확인: 김지영 · **위양성**: 실제로는 정상인데 AI가 **폐렴(Positive)**으로 판정한 경우

`POST /api/v1/medical-records → 201` · `POST /api/v1/medical-records/{id}/predict → 201`

- 폐렴이 없는 **정상 흉부 X-Ray**를 진료기록으로 등록하고 **AI 예측 결과보기**를 눌렀습니다.
- 결과: **Positive, 신뢰도 71.2%, `efficientnet_b0-5fold`, `v1`**. 실제로는 정상인데 폐렴으로 판정된 **위양성(False Positive)** 사례입니다.
- 프론트는 맞은 양성 결과와 똑같이 빨간색 행으로 보여 주기 때문에, **화면만 보고는 오판인지 구분할 수 없습니다.**

![정상 X-Ray 위양성](images/day7/21_false_positive.png)

> 이미지 출처: [Radiopaedia – Normal chest radiograph (female) 2](https://radiopaedia.org/cases/normal-chest-radiograph-female-2) (작성자와 rID는 케이스 페이지에 표기), [CC BY-NC-SA 3.0 수정 라이선스](https://images.radiopaedia.org/licence), 비영리 교육 목적 사용
> 의료 교육 사이트에 **정상 소견**으로 공개된 익명 흉부 X-Ray이며, 우리 팀이 수집한 환자 데이터가 아닙니다. 예측값은 API·UI 동작 확인용으로 의료적 판단 근거가 아닙니다.

|---|---|---|---|
| 팀 공용 샘플 X-Ray (3절 12번) | 라벨 정보 없음 | Negative 83.28% | ➖ 정답 미상 |
| 폐렴 X-Ray (5-A) | Wikipedia 폐렴 예시 | Positive 99.47% | ✅ 맞음 |
| **정상 X-Ray (이 캡처)** | Radiopaedia 정상 소견 사례 | **Positive 71.2%** | ⚠️ 위양성 |

**모델의 판정 기준과 신뢰도 읽는 법**

`worker/model.py`는 5개 Fold 모델이 산출한 **폐렴 점수(0~1)의 평균**을 기준값과 비교합니다.

| 항목 | 내용 |
|---|---|
| 판정 기준 | 폐렴 점수 **0.4 초과**면 Positive |
| 화면의 신뢰도 | Positive면 `폐렴 점수 × 100`, Negative면 `(1 − 폐렴 점수) × 100` |
| 기준값의 의미 | 0.5보다 낮은 기준이라 **Positive로 판정되는 범위가 넓습니다.** (선정 이유는 개발 기록으로 확인하지 않았습니다) |

| 화면 결과 | 모델이 산출한 폐렴 점수 | 해석 |
|---|---|---|
| Positive 99.47% (5-A) | 0.9947 | 모델이 강하게 폐렴으로 판단 |
| **Positive 71.2% (이 캡처)** | 0.712 | 기준 0.4는 물론 0.5도 넘음 → **기준값 때문이 아니라 모델 자체가 틀린 경우** |
| Positive 40~50% | 0.40~0.50 | 점수는 0.5 미만이지만 기준을 넘어 Positive. 판정이 바뀌기 쉬운 경계 구간 |
| Negative 83.28% (3절 12번) | 0.1672 | 모델이 정상으로 판단 |

- 이번 위양성은 **신뢰도 71%로도 틀릴 수 있다**는 것을 보여 줍니다. 신뢰도는 "모델이 얼마나 확신하는가"이지 "정답일 확률"이 아닙니다.
- 이 시스템은 의사의 판독을 **보조**하는 도구이므로, AI 결과는 의료진 판독으로 최종 확인해야 합니다.
- 5-E(고양이 사진)와 회색 테스트 이미지의 Positive 판정은 **X-Ray가 아닌 입력**에 대한 결과라서, 정상 X-Ray를 잘못 판정한 위양성과는 구분했습니다.
- 판정 1~2건으로는 위양성 **비율**을 말할 수 없습니다. 비율은 라벨이 있는 테스트 데이터 전체로 평가해야 합니다.

> 개선 방향: 결과 표 옆에 **"AI 판정은 진단 보조용이며 의료진 확인이 필요합니다"** 안내 문구 표시, 신뢰도 50% 미만 Positive에는 **"경계 판정"** 표시 추가.

- 환자 목록은 `innerHTML`로 표를 그리는데, PR #42에서 추가한 `utils.escapeHtml()`이 `<`, `>`를 `&lt;`, `&gt;`로 바꿔서 **글자 그대로** 보입니다. 테스트 중 알림창은 한 번도 뜨지 않았습니다.

![환자 목록에서 글자로 표시](images/day7/24_xss_patient_list.png)

- 환자 상세는 `innerText`로 이름을 넣기 때문에 원래부터 안전하며, 역시 글자 그대로 표시됩니다.

![환자 상세에서 글자로 표시](images/day7/25_xss_patient_detail.png)

### 6-D) 이미지가 아닌 파일 업로드 → 415

- 파일 선택 칸은 `accept="image/*"`로 이미지만 보이게 하지만, 파일 형식을 "모든 파일"로 바꾸면 다른 파일도 고를 수 있습니다.
- 텍스트 파일(`not_image.txt`)을 X-Ray로 올리자 백엔드가 **파일 앞부분의 서명(PNG·JPEG)**을 검사해 **415 Unsupported Media Type**을 반환하고, **"JPG, PNG 이미지만 업로드할 수 있습니다."** 알림이 뜹니다.
- 프론트의 `accept`는 편의 기능일 뿐이고, **실제 차단은 백엔드 검증**에서 이뤄진다는 것을 확인했습니다.

![이미지가 아닌 파일 415](images/day7/26_upload_not_image.png)

### 6-E) 차트 번호 중복 → 409

- 김환자에게 `CH-2026-001`로 진료기록을 등록한 뒤, **같은 차트 번호**로 한 번 더 등록했습니다.
- 백엔드가 **409 Conflict**를 반환하고 **"이미 사용 중인 차트 넘버입니다."** 알림이 뜹니다. 진료기록 목록에는 처음 등록한 1건만 남아 있습니다.

![차트 번호 중복 409](images/day7/27_chart_duplicate.png)

## 부록: 화면에서 직접 호출하지 않는 엔드포인트

백엔드에는 있지만 화면에 호출 버튼이나 입력 폼이 없는 API입니다. 토큰 재발급을 뺀 나머지는 이번 화면 검증 대상에서 제외했습니다.

| 메서드 | 경로 | 비고 |
|---|---|---|
| PATCH | `/api/v1/medical-records/{record_id}` | 진료기록 수정. 화면과 `apis.js` 호출 함수 없음 |
| DELETE | `/api/v1/medical-records/{record_id}` | 진료기록 개별 삭제. 환자 삭제 시의 연쇄 삭제와는 별개 |
| POST | `/api/v1/users/refresh` | 화면 버튼은 없고, 액세스 토큰이 만료되면 `apis.js`가 자동 호출 |
| GET · POST · PUT · DELETE | `/practice_api/users...` | 수업용 연습 API |
| GET | `/healthcheck` | 서버 상태 확인용 |
| GET | `/docs`, `/redoc` | FastAPI 자동 문서 |

> 화면 주소(`/login`, `/patients`, `/my-page`, `/admin/users` 등)는 모두 `GET /{path:path}`에서 같은 `index.html`을 받고, `app.js`가 주소에 맞는 화면을 그립니다.
